## 并发写与 `FS_STALE_VERSION`（硬约束）

`edit` / `write` 返回 `file changed since it was read` 时，说明读过之后文件被外部改过。**这个判定基于 stat 元数据（inode/mtime/ctime），不是内容 hash**——所以你自己的写和别人（GUI、插件市场、其他会话）的写在令牌上完全一样，**无法从错误里分辨是谁**。

必须按三段式处理，**不允许含糊报告「已完成」**：

1. **重读全文**（不是只读目标行）
2. **对比两类差异**：
   - 「计划内变更」——你本来要改的那处
   - 「**计划外差异**」——外部同时引入的其他改动
3. 按结果报告：

   | 情形 | 动作 |
   |---|---|
   | 目标已达成 + 无计划外差异 | 报告「状态已由外部达成，本次 edit 未生效」 |
   | 目标已达成 + **有计划外差异** | 报告「目标已达成，但外部同时引入了 X、Y」**并逐条列出** |
   | 目标未达成 | rebase 到最新内容重做，不得跳过 |

**禁止**：只看目标行是否达成、不检查整文件差异就报完成。状态漂移被隐藏，比改动失败更危险。

> **边界声明**：这里的「重读全文 / 全量 diff」**只针对本文件**——目的是确认「这个文件的现状是否与我以为的一致」。它**不等于**扩大验证范围：不触发全量 build / test、不审查无关文件、不追查其他改动的来源（只报告发现了什么，不负责修）。与「验证按委派范围执行，不自行扩大为全量」不矛盾。

## 执行器环境契约（通用原则 + 探测式自适应）

### A. 通用原则（任何环境成立，强制）
1. **自包含**：脚本不依赖会话上下文；所需事实（路径/清单/约束）写进任务或 prompt。
2. **先验证再批量**：第一次使用本环境的模块加载/API/命令写法前，先跑**最小探针**确认可用，再批量执行；不要整批盲试。
3. **错误可回传**：执行失败必须把错误原样回传（错误消息/调用栈/退出码），供上层判断重试/换策略。

### B. 环境探测流程（写正式脚本前先做一次）
1. 写最小探针，**依次尝试候选写法**（如：`const fs = await import('node:fs')` → `require('fs')` → 静态 `import`），分别运行；
2. 记录**哪种写法通过**，用该写法写正式脚本；探针输出记入结果，避免重复探测；
3. 若全部候选失败：**回传探针错误并停止，不要反复盲试**（盲试成本 = 失败调用 × 推理 token）。
