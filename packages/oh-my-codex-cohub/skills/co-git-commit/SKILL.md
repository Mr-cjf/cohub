# co-git-commit：Git 提交

你是 CoHub 的 Git 提交工作流，负责把当前变更整理成一次结构化提交。

## 定位与触发

- 触发：用户要求"提交""commit""git commit""提交代码"。
- 仅做提交，不做发版、不打 tag、不 push。明确提到发版/发布或"提交并发版"时，改用 [co-git-commit-release](../co-git-commit-release/SKILL.md)。
- 工作目录是**用户目标仓库**（当前 Git 仓库根），不是插件安装缓存或开发源仓库；不读写 `~/.codex/plugins/cache`。

## 执行流程

### 1. 审查工作区状态

并行执行只读命令收集现状，区分三种状态：

- `git status` — 工作区整体状态
- `git log --oneline -10` — 最近提交历史（已提交）
- `git diff --cached` — 暂存变更
- `git diff` — 未暂存变更
- `git branch --show-current` — 当前分支

**已提交 / 暂存 / 未提交**三者严格区分，报告时如实说明。

### 2. 确定提交范围与授权

先只读核对**三种情况**，再谈授权：

- **已有暂存**：`git diff --cached` 已暂存的内容——是用户此前暂存的，还是本流程拟提交的，必须分清。
- **未暂存**：`git diff` 中未暂存的内容。
- **同文件混合 hunk**：同一文件既含暂存内容又含未暂存 hunk，或用户授权变更与未授权变更同在一个文件。

**授权是内容级（hunk/变更块）而非文件级**：确认的是"哪段变更可提交"，而不是"哪个文件可提交"。`git add <file>` 会把该文件**所有**变更一并暂存，即使文件在授权清单里，也可能夹带同文件内用户未授权的 hunk。

- **无法可靠区分 hunk 归属 → 停止并询问用户**，不猜测、不擅自整文件暂存。
- 可先只读展示每个文件的 hunk 边界（`git diff` / `git diff --cached` 的分块）供用户逐块确认；**不把交互式 `git add -p` 当作当前环境唯一解法**，也不写复杂脚本模拟它——只读识别后询问即可。
- 当前分支若为远程默认分支或用户声明的集成分支，提示该分支提交直接进入集成历史，需用户明确确认后再继续。
- 无任何变更（无暂存且无未暂存）→ 告知工作区干净，流程终止。
- 只有未暂存变更 → 列出文件与 hunk 边界，询问用户需要提交哪些内容。

### 3. 秘密扫描

检查待提交内容中的敏感信息：API Key、token、密码、私钥、真实凭据等。发现则提示用户排除或改写，处理完成前不提交。

### 4. 生成真实 diff 的中文变更表格

基于 `git diff --cached`（含用户明确纳入的未暂存文件）的**真实内容**生成摘要表格，不凭空编造：

| 文件 | 变更类型 | 变更摘要（中文） | 变更意图 |
|------|---------|-----------------|---------|
| 路径 | 新增/修改/删除 | 该文件真实改了什么 | 新功能/Bug 修复/重构/文档/配置/测试/构建 |

- 摘要与意图来自真实 diff 内容与文件路径判断，逐文件分析后填入。
- 可参考 `git log` 中历史提交的表格样式与延续性，但表格内容**只来自本次真实 diff**，不盲目累积历史行。
- 上次提交无表格段落**不等于分支首提交**：核实基准后用 `git log --oneline <基准>..HEAD` 统计分支提交数，辅助延续性判断。
- 基准确定：优先用户指定；否则只读核实远程默认分支（本地 `git symbolic-ref refs/remotes/<remote>/HEAD`，未配置时 `git ls-remote --symref <remote> HEAD` 只读查询），**不猜 master/main/origin**；无法确认则询问用户。

### 5. 生成提交信息

Conventional Commits 格式：

```
<type>(<scope>): <简短描述>

## 变更概述
- 3-5 个要点概括本次变更的核心内容

## 详细说明
- 具体的代码变更和实现细节

## 影响范围
- 受影响的模块或功能

## 变更摘要表格
<上一步生成的中文表格>

## 测试说明
- 已执行的验证 / 建议执行的验证
```

提交类型：

| Type | 用途 | Type | 用途 |
|------|------|------|------|
| `feat` | 新功能 | `fix` | Bug 修复 |
| `refactor` | 重构 | `docs` | 文档 |
| `test` | 测试 | `chore` | 构建/工具 |
| `ci` | CI/CD | `perf` | 性能优化 |

scope 优先用模块名，跨模块用 `cross-module` 或省略。

### 6. 预览与授权确认

- 展示完整提交信息 + 文件清单 + 变更表格。
- **分清"生成消息"与"实际 commit 授权"**：展示预览不等于授权提交。
- 用户已有明确授权（如"可以提交""直接提交"）可复用，不无意义重复确认；未授权则等待明确确认。
- 确认后执行提交，但先满足以下条件：
  - **只读核对**待提交内容与用户已确认授权一致；仍含未授权 hunk 则不得提交。
  - **保留用户索引状态**：不 `git reset`、不撤销用户已有暂存；本流程不为此清空或重置索引。
  - 用户索引中已有**无关暂存**内容时，**不直接 `git commit`**（会把无关索引一并提交）；先向用户说明索引归属并取得处置意见，再决定提交方式。
  - 同文件含未授权 hunk 而无法精确分离 → 停止并请用户处理，不强行提交。

```bash
git add <已获内容授权且不含未授权 hunk 的路径>
git commit
```

- 提交失败 → 报告真实错误并停止。

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| `git add .` 夹带未授权文件 | 只暂存已获授权的内容，逐项列出 |
| `git add <文件>` 夹带同文件未授权 hunk | 按内容（hunk）授权而非文件全授权；无法分离则停止询问 |
| 提交时把用户已有暂存的无关内容一并带入 | 不直接 `git commit` 现有索引；先说明索引归属并取处置意见 |
| 为分离 hunk 用 `git reset` 撤销用户暂存 | 保留用户索引状态，不擅自清空/重置索引 |
| 把交互式 `git add -p` 当唯一解法或写脚本模拟 | 只读展示 hunk 边界后询问用户 |
| 表格内容凭猜测编写 | 表格来自真实 `git diff` |
| 把历史表格行原样累积 | 只从本次真实 diff 生成，参考历史仅作样式与延续性判断 |
| 展示提交信息后直接 commit | 区分消息生成与 commit 授权，等待明确确认 |
| 在插件安装缓存目录执行 | 始终在用户目标仓库工作 |

## 硬性规则

- 授权按**内容（hunk）**而非文件；不 `git add .`，不夹带用户未授权变化（含同文件未授权 hunk）。
- **保留用户索引状态**：不 `git reset`/撤销用户暂存；索引含无关暂存时不直接 `git commit`。
- 无法可靠区分 hunk 归属 → 停止并询问用户，不猜测。
- 不静默吞掉失败；提交失败如实报告。
- 本技能范围只到 commit：不发版、不打 tag、不 push。
- 始终中文输出。
