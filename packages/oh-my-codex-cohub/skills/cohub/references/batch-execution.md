# Codex 批量操作

适用于同一任务中的多文件修改、多个子代理和多条命令。工作流、完整委派包、状态与回传格式遵循[CoHub 效率规范](efficiency.md)；本文件说明文件、命令和共享资源的冲突处理。只使用当前会话实际提供的工具。

## 先判断依赖和写入范围

- 独立读取、搜索及无写入冲突的命令可在一次工具编排中并行发出，逐项收集结果。
- 读取某一步产出、消费生成文件、先构建后测试等存在依赖的操作按顺序执行。
- 文件、目录、锁文件、生成物、数据库及服务端口都可能是共享写入资源。操作不同源文件但写入同一 `dist/`、更新同一 lockfile 或使用同一测试数据库时，也要串行或隔离。
- 同一模块的接口与实现等紧密相关修改尽量交给一个执行者；只有明确独立的范围才拆给多个代理。

## 批量改文件

1. 确认本任务的文件归属和当前改动；先集中搜索，再将已确定的独立文件读取打包，避免逐文件往返。大文件只读取相关片段。
2. 根据读取结果准备一组相关修改。同一文件的多处改动合并，关联文件可放在一次 `apply_patch` 中提交；写入前须确认所有者已结束前一次写操作。
3. 手工代码修改使用当前环境提供的补丁工具。结构化数据使用解析器；机械迁移、格式化可使用项目现有脚本，范围限定为本任务文件。
4. 校验格式及补丁结果。发现上下文已改变时重读受影响文件，再修补；不要用旧内容覆盖其他代理或用户的修改。
5. 多文件修改结束后由指定验证者统一运行相关构建、测试或 lint。行为变更通常先用明确契约的失败测试验证预期；用户指定实现后再更新测试等顺序时，按其明确依赖执行，在交付前补齐验证，不逆转依赖来凑测试先行流程。

执行者收到 `implementation-only` 时只提交本批修改和检查摘要，状态记为 `implemented`，明确“验证待统一执行”。验证负责人收到整批产出并通过相关检查后，才将任务标记为 `completed`。没有这个约定时，执行者自行完成必要验证。低风险文案或格式变更按项目要求检查，不为凑流程新增测试。

## 并行派代理

- 规划时为每项任务列出依赖、可读路径、独占写入范围、产出、验收标准和验证负责人；共享目录或生成输出只有明确互不覆盖时才可并行分配。
- 委派附所用 `SKILL.md` 的绝对路径，并保留原技能指令、前置结论、写入归属和统一验证约定。只派相关角色；紧密相关的小任务可合并。
- 就绪队列、模型参数批量解析、原生 spawn 连续发送、宿主容量、等待与失败记账统一遵循[效率规范](efficiency.md)的 `dispatch_prepare` / `dispatch_send` 契约。

## 批量执行命令

- 每条命令给出自己的工作目录、任务别名和读写范围。独立命令在一次编排中并行运行，各自保留退出码、标准输出、错误输出和会话 ID。
- 使用会话提供的并行工具。若环境提供 `functions.exec` 和 `tools.exec_command`，可将独立调用放入 `await Promise.allSettled([...])`，随后检查每项结果；某项 rejected 或退出码非零时仍能报告其他命令的结果。
- 构建依赖安装、测试依赖构建等步骤逐项执行，前置失败时暂停其下游。相同构建输出、锁文件或测试状态的命令由一个负责人串行执行。
- 命令通过各自工具调用编排，保留清晰的归属和结果；不要用分号拼成一长串命令来伪装批处理。陌生命令/API 先验证最小调用，确认参数和工作目录后再扩大批次。
- 返回会话 ID 表示仍在运行，记录并继续等待，直到验证命令有最终结果。用户需要的开发服务记录地址和会话归属，保持服务运行。

## 整批收尾和失败处理

- 代理失败、依赖阻断和重试按[效率规范](efficiency.md)记账；命令失败仍保留真实退出码与错误结果，不能因其他项成功而隐藏。
- 统一验证前等待相关代理写入和命令结束，检查 diff 与文件归属。选取覆盖整批行为的项目检查，一次运行；通过后不因每项交付而重复同一整套构建。
- 验证失败时，将具体错误及文件范围交给对应所有者修复；修复完成后重跑受影响的检查。最终报告批次改动、验证结果和仍未完成的项。

## 调度示例

若 A 修改 `src/api.ts`，B 修改独立的 `styles/theme.css`，C 更新依赖 A 的 API 测试，D 编译整个项目：A、B 就绪后立即派发；A 完成后 C 立即就绪并进入派发队列，不必等待 B。D 等待 A、B、C 的写入全部结束。实际并行数遵循运行时容量；多个构建命令即使来自不同代理，只要写同一输出目录，也不能并行。
